# 二、但现在最大的残余问题不是 1/6 UNCERTAIN，而是容量模型不一致

这个问题代码自己已经明确记录：

> ```
> v2: ... hard token cap (rx_cap_tokens); CA: airtime budget sum tau <= T_air (distinct capacity primitives remain a documented open item)
> ```

也就是说目前正式 Gate 已经承认两种算法使用的是**不同 capacity primitive**。

而进一步看实现，差异比“token vs airtime”还更深。

### FRIDS-v2 当前顺序

当前 v2 在拥塞模式中基本是：

[
\text{sensing}
\rightarrow
\boxed{\text{link Bernoulli}}
\rightarrow
\text{successful offers}
\rightarrow
\boxed{\text{token-cap admission}}
\rightarrow
\text{fusion}.
]

代码明确是先检查 `U_link <= delivery`，成功后才放入 receiver offer list，然后再做 `rx_cap_tokens` 下的无放回 admission。

因此：

> **链路失败的 token 根本没有消耗 receiver capacity。**

这实际上是一个比较乐观的 MAC 模型。

### CA-FRIDS 当前顺序

CA 则是：

[
\text{sensing}
\rightarrow
\text{offer}
\rightarrow
\boxed{\sum c_{ij}\le1\text{ admission}}
\rightarrow
\boxed{\text{link Bernoulli}}
\rightarrow
\text{fusion}.
]

而且代码明确规定：

> admitted transmission 即使最后 link outage，airtime 也已经花掉。

这从通信物理上反而更合理：

[
\text{resource reservation/transmission}
\rightarrow
\text{channel outcome}.
]

所以现在的比较是：

[
\boxed{
\text{v2：成功后才占容量}
\quad\text{vs}\quad
\text{CA：先占容量再看成功}
}
]

并不是完全相同的物理资源模型。

这意味着当前 `+11.7%` 很有价值，甚至 CA 在某种意义上吃了更严格的资源约束，但**论文里还不能把它完全解释为“CA scheduler 本身带来的 11.7% 增益”**。

我建议下一轮定义成：

具体执行顺序如下：

| 优先级   | 操作                                              | 是否改变算法       |
| -------- | ------------------------------------------------- | ------------------ |
| **P0**   | 建立共享 `airtime_admission` primitive            | 否                 |
| **P0**   | v2 改成 `offer → admission → link outcome`        | 否，只纠正物理口径 |
| **P0**   | 两者统一 (c_{ij}=\tau_{ij}/T_{\rm air})           | 否                 |
| **P0**   | owner-local (c=0) 两边一致                        | 否                 |
| **P0**   | 两边统一 offer/admitted/link-drop/cap-drop ledger | 否                 |
| **P0**   | 重新跑 3geom Gate                                 | 是实验重认证       |
| **随后** | 若仍 5P+1U，再做 CS escalation                    | —                  |
| **之后** | expected-(P_D) primal-dual CA                     | 真正算法升级       |

建议共享一个函数，例如：

```python
admit_airtime_offers(
    offers,
    tau,
    t_air,
    policy=...,
    policy_rng=...,
)
```

物理约束统一为

[
\sum_{i\in\mathcal A_j(t)}
\frac{\tau_{ij}}{T_{\rm air}}
\le 1.
]

FRIDS-v2 使用**exchangeable neutral admission**；

CA-FRIDS 使用当前 **density admission**。

这样两种方法共享相同的 feasible set，只区别：

[
\text{谁生成 offer}
]

以及

[
\text{如何优先 admission}.
]

# 五、还有两个很小的 P0/P1 残差，可以在这一轮一起修掉

### 1. `tx_attempts` 的名字仍然容易误导

代码现在实际上是：

# [ N_{\rm offer}

N_{\rm admitted}
+
N_{\rm capacity-drop},
]

以及

# [ N_{\rm admitted}

N_{\rm delivered}
+
N_{\rm link-drop}.
]

这是正确的。

但变量仍叫：

```text
tx_attempts_per_uav
```

而 return 附近的注释还写成“airtime committed”，实际上 capacity-dropped offer 并没有计入 `load_now` 的 airtime。

所以建议正式改名：

```text
offer_attempts_per_uav
admitted_tx_per_uav
delivered_tx_per_uav
```

于是以后不能再写：

> “CA reduces transmissions by 6.6%”

如果算的是：

```text
ca_tx = tx_attempts_per_uav
```

应该写：

> “CA reduces report offers / transmission requests by 6.6%.”

真正的 physical TX rate 应用：

```text
rx_admitted_per_uav
```

例如当前 geom2 congested：

[
\text{offer rate}=0.9341,
]

但

[
\text{admitted TX}=0.7792.
]

两者差异很明显。

这个一定要在论文前纠正。

### 2. 结果 provenance 还差最后一步

当前 commit 已经是：

```text
2d4b1ce
```

但正式结果文件里记录的仍是：

```text
"git_sha": "22ec9d3"
```

原因非常清楚：正式门是在 commit 前的 working tree 上跑完，再把代码和结果一起 commit。

这并不说明结果是假的，但论文复现实验会遇到：

> result artifact 说自己来自 `22ec9d3`，实际代码对应 `2d4b1ce`。

建议 provenance 以后至少记录：

```text
git_commit
git_tree
git_dirty
config_hash
```

最简单方案就是**容量统一完成后，在 clean committed HEAD 上正式重跑一次**。不要手工修改 JSON 中的 SHA。
